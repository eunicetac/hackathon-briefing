How messages work in this system

Messages in this C3 system are sent in binary format over a Kafka broker. Before a system can publish or subscribe to data, it must first send a Connection Request to establish a session with the broker.

Each binary message follows an FSPEC (Field Specification) pattern — a bitmask at the start of the message that tells the receiver which fields are present. Fields marked M (Mandatory) are always present. Fields marked O (Optional) may or may not be present depending on the FSPEC. Fields marked X (Excluded) are reserved and not used.

Your challenge is to build an agent that can interpret a plain-language or structured integration requirement and generate the correct binary gateway code to encode and send these messages.

Message schema 1 — Connection Request

Purpose: Establishes a connection to the Kafka broker before any data can be published or subscribed to. Must be sent first.

Transport: Binary over Kafka. Topic 10 = Aerodrome topic. Connection ID: use 0. System ID: use 15000.

Field ID Field Name Data Type Bytes Range / Values M/O
—FSPECunsigned1Bitmask — see FSPEC tableM
1Topicunsigned20–65535. Use 10 for Aerodrome topicM
2Connection IDunsigned2Use 0M
3Kind of Connectionunsigned11 = Publisher, 2 = SubscriberM
4System IDunsigned2Use 15000M
5System Modeunsigned11 = Operational, 2 = SimulationM
6R.E. Field——Reserved expansionO
7S.P. Field——Special purposeO
Example — encode a Connection Request (Subscriber, Operational)
import struct

# FSPEC: fields 1–5 all mandatory (bits 7–3 set = 0b11111000 = 0xF8)
fspec   = 0xF8
topic   = 10      # Aerodrome topic
conn_id = 0       # Connection ID
kind    = 2       # Subscriber
sys_id  = 15000   # System ID
mode    = 1       # Operational

msg = struct.pack(
    '>BHHBHB',   # big-endian: 1B fspec, 2B topic, 2B conn_id, 1B kind, 2B sys_id, 1B mode
    fspec, topic, conn_id, kind, sys_id, mode
)

print(f"Connection Request ({len(msg)} bytes): {msg.hex().upper()}")
# Expected: F8 000A 0000 02 3A98 01
Message schema 2 — Aerodrome

Purpose: Published as a Kafka message to subscribers with the latest aerodrome data. Contains position, boundary, timing, and identity fields.

Key encoding rules: Aerodrome Name is a fixed 10-character string padded with spaces. Timestamps are milliseconds since Unix epoch (UTC midnight 1/1/1970). Position coordinates are in arc-milliseconds. CRC is a SHA-256 hash of the full payload excluding the CRC field itself.

Field ID Field Name Data Type Bytes Range / Notes M/O
—FSPECunsigned2Bitmask — 2 bytes for this messageM
1Aerodrome IDunsigned80–100,000. Use running numberM
2Last Update Timeunsigned8ms since Unix epochM
3Aerodrome Name10-char string10Alphanumeric, pad with spacesM
4Aerodrome Typeunsigned11 = Public, 2 = PrivateM
5Aerodrome Start Timesigned8ms since epoch. -1 = no statementM
6Aerodrome End Timesigned8ms since epochM
7Upper Boundaryunsigned20–5000 feetM
8Lower Boundaryunsigned20–5000 feetM
9Aerodrome Positionrepeatingvariable1B count (3–100), then N × (4B lon + 4B lat) in arc-msM
10CRCchar string32SHA-256 of full payload excluding CRCM
Example — encode an Aerodrome message
import struct, hashlib, time

# FSPEC: fields 1–10 all mandatory
# Byte 1: fields 1–7 set (bits 7–1) + FX bit = 0b11111111 = 0xFF
# Byte 2: fields 8–10 set (bits 7–5) = 0b11100000 = 0xE0
fspec = 0xFF, 0xE0

aerodrome_id   = 1
now_ms         = int(time.time() * 1000)
name           = b'CHANGI    '   # 10 bytes, space-padded
aero_type      = 1              # Public
start_time     = now_ms
end_time       = now_ms + 86400000  # +24 hours
upper_boundary = 500           # feet
lower_boundary = 0

# Position: 4 polygon points (lon/lat in arc-milliseconds)
# Singapore approx: 103.8°E, 1.35°N
# 103.8° × 3600000 ms/° = 373,680,000 arc-ms
points = [
    (373_680_000, 4_860_000),
    (373_800_000, 4_860_000),
    (373_800_000, 4_740_000),
    (373_680_000, 4_740_000),
]

# Build payload (without CRC)
payload = struct.pack('>BB', *fspec)
payload += struct.pack('>Q', aerodrome_id)
payload += struct.pack('>Q', now_ms)
payload += name
payload += struct.pack('>B', aero_type)
payload += struct.pack('>q', start_time)
payload += struct.pack('>q', end_time)
payload += struct.pack('>H', upper_boundary)
payload += struct.pack('>H', lower_boundary)
payload += struct.pack('>B', len(points))
for lon, lat in points:
    payload += struct.pack('>ii', lon, lat)

# Append SHA-256 CRC
crc = hashlib.sha256(payload).digest()   # 32 bytes
full_msg = payload + crc

print(f"Aerodrome message ({len(full_msg)} bytes)")
print(f"Hex: {full_msg.hex().upper()}")
Coordinate conversion tip
To convert decimal degrees to arc-milliseconds: multiply by 3,600,000. E.g. 103.8°E × 3,600,000 = 373,680,000. To convert back: divide by 3,600,000.
Connection types — Publisher vs Subscriber

The Kind of Connection field in the Connection Request determines how your system interacts with the broker. Choose the right mode for your use case:

ValueTypeDescriptionUse when
1 Publisher Sends messages to the broker on a topic Your system generates aerodrome data and pushes it out
2 Subscriber Receives messages from the broker on a topic Your system consumes aerodrome data from another source
Important
The Connection Request must be sent and acknowledged before any Aerodrome messages can be published or received. Your gateway code should handle the connection handshake as a first step.
ASTERIX standard — reference & decoders

The message schemas above follow conventions from the EUROCONTROL ASTERIX (All Purpose STructured EUROCONTROL SuRveillance Information EXchange) standard — a binary messaging format widely used in ATM surveillance systems. Familiarity with ASTERIX will help you understand the FSPEC pattern, field encoding, and binary layout used in this starter pack.

Official Standard
EUROCONTROL ASTERIX — Official Specification
The authoritative source for ASTERIX category definitions, encoding rules, and field specifications. Reference this when you need to understand how fields are structured at the bit level.

What your agent should be able to do

Use these starter materials as inputs to train or prompt your agent. A strong submission will demonstrate an agent that can:

1. Interpret a plain-language requirement — e.g. "create a subscriber connection to the aerodrome topic in simulation mode" → generate the correct binary Connection Request.

2. Generate valid binary gateway code — correct field order, data types, byte lengths, FSPEC bitmask, and SHA-256 CRC.

3. Handle ambiguity — if a requirement is underspecified (e.g. "connect to the broker" without specifying Publisher or Subscriber), the agent should ask a clarifying question rather than assume.

4. Validate output — use the ASTERIX decoder libraries above to verify that generated messages can be parsed back correctly.
